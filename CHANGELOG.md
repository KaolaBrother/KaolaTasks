- `@kaola/forge-adapters` (#13 webhook receivers + registerWebhook): `ForgeEvent` is no longer `unknown` — `{ type: 'pull_request'; state: 'merged' | 'closed'; pr_url: string; repo: { full_name: string } }`. New `WebhookSignatureError extends Error` (`name === 'WebhookSignatureError'`), thrown by `parseWebhook` on a bad/missing signature or secret; `parseWebhook` returns `null` (never throws) for a signature-valid-but-irrelevant delivery (ping, non-`pull_request`/non-`Merge Request Hook`, non-`closed` action, unparseable JSON, missing `pr_url`/`repo.full_name`). `CreateForgeAdapterOptions` gained `webhookSecret?: string`. `registerWebhook(cred, repo, callback)` and `parseWebhook(headers: Headers, body: unknown)` are implemented on all three adapters (were `notImplemented`); `commentOnIssue` still throws `Error('not implemented')` (#14, out of scope). `parseWebhook`: missing/empty `webhookSecret` throws `WebhookSignatureError` before any header check; verifies against the **raw** body string/Buffer (never a re-serialized JSON object), then `JSON.parse`s (parse failure → `null`, not a throw). Per-forge signature check: GitHub `X-Hub-Signature-256` header, expected `sha256=${createHmac('sha256', secret).update(rawBody).digest('hex')}`, compared via a length-checked `timingSafeEqual` wrapper (`timingSafeEqualStrings`); Gitea `X-Gitea-Signature` header, same HMAC digest **without** the `sha256=` prefix; GitLab `X-Gitlab-Token` header, plain `timingSafeEqualStrings` against `webhookSecret` (legacy secret-token scheme, not GitLab's newer `webhook-signature`/`signing_token` HMAC — explicitly out of scope per the ruling). Event mapping: GitHub/Gitea (`mapGithubShapedEvent`) require header `x-github-event`/`x-gitea-event === 'pull_request'` and payload `action === 'closed'`; `state` is `'merged'` when `pull_request.merged === true` else `'closed'`; `pr_url` = `pull_request.html_url`; `repo.full_name` = `repository.full_name`. GitLab (`mapGitlabEvent`) requires header `x-gitlab-event === 'Merge Request Hook'` and `object_attributes.state` in `('merged', 'closed')`; `pr_url` = `object_attributes.url`; `repo.full_name` = `project.path_with_namespace`. `registerWebhook`: GitHub `POST https://api.github.com/repos/{owner}/{repo}/hooks` body `{ name: 'web', events: ['pull_request'], config: { url: callback, content_type: 'json', secret, insecure_ssl: '0' } }`; GitLab `POST {baseUrl}/api/v4/projects/{encodeURIComponent(repo.full_name)}/hooks` body `{ url: callback, merge_requests_events: true, token: secret }` (legacy `token`, not `signing_token`); Gitea `POST {baseUrl}/api/v1/repos/{owner}/{repo}/hooks` body `{ type: 'gitea', events: ['pull_request'], config: { url: callback, content_type: 'json', secret }, active: true }` (owner/repo each individually `encodeURIComponent`-ed, same as the GitHub branch — a security-review fix, R2, non-blocking). All three reject after a non-OK response with `registerWebhook: ${kind} responded ${status}`; auth headers reuse the existing per-kind `authHeaders()`. GitHub/GitLab/Gitea host rules for `registerWebhook` are unchanged from `getPullRequest`/`importIssue` (GitHub always `https://api.github.com`; GitLab/Gitea use constructor `baseUrl`); `parseWebhook` never fetches. - `@kaola/server` (#11 PR polling): new `apps/server/src/poller.ts` exports `pollPendingReviews(db: AppDb): Promise<void>` — the only driver of `待验收` → `已完成`/`已退回`. Selects `tasks` where `status === '待验收'`; for each, reads the latest `submissions` row by `id` for that task (`orderBy(desc(submissions.id)).limit(1)`), decrypts the task's credential (profile or inline, same branch as `claimTask`) and calls the forge adapter's `getPullRequest({ token }, submission.prUrl)`. `state: 'open'` leaves the task untouched. `state: 'merged'` → `transitionTaskStatus('待验收', '已完成')`, `submissions.pr_state` set to `'merged'`. `state: 'closed'` → transition to `已退回`, `pr_state` set to `'closed'`. Both writes plus one `insertAuditEvent` run inside one `db.transaction`; event `type` `状态迁移`, `actorUserId: null` (system-driven, mirrors lease-expiry events), `details` `{ task_id, from: '待验收', to, pr_url }` (no `summary` key, unlike MCP `submit_pr`'s own `状态迁移` event). Never throws: a missing/undecryptable credential, an unreachable forge, a non-OK response, or a DB fault on one task's write phase is caught and only skips that task's row — the rest of the pending set is still polled, and `pollPendingReviews` itself always resolves (never rejects), which is required because it can be driven by `setInterval`. Tasks in any other status (`待认领`/`进行中`/`已完成`/`已取消`/already-`已退回`) are never selected and never fetched as PRs. The pre-existing poster `PATCH /api/v1/tasks/:publicId` `已退回` → `待认领` edge is unchanged and still works after a poller-driven `已退回`; prior `状态迁移` events and the `submissions` row survive that reopen unmodified. `vault.ts`'s `insertAuditEvent` first parameter is now typed as a structural `{ insert: AppDb['insert'] }` (not the full `AppDb`) so it also accepts a `db.transaction` handle. `buildApp({ pollIntervalMs? })`: new optional option, registered in its own child plugin (mirrors `mcp.ts`'s bearer context) so its `onClose` hook (which `clearInterval`s) runs before the root db-close hook regardless of registration order. Omitted or `<= 0` → no `setInterval` call at all. A positive integer → exactly one `setInterval(fn, pollIntervalMs)`, with an in-flight guard so an overrunning poll pass is never re-entered by the next tick; `app.close()` clears the timer. Production `index.ts` computes `pollIntervalMs` from `process.env.POLL_INTERVAL_MS` (unset or `''` → `60000`; otherwise `Number.parseInt(value, 10)`) and passes it into `buildApp`. Still no REST `submit_pr` and no webhook route — `pollPendingReviews` (on-demand in tests, or on the `pollIntervalMs` timer) is the only thing that ever moves a task out of `待验收`.
